# 报告模板

按下面的结构写。标题和字段名保持不变，校验脚本依赖这些字段。

````markdown
# 代码审查报告

- 审查时间: YYYY-MM-DD HH:mm
- 审查范围: <working-tree | branch | paths | repo>
- 基准: <分支、提交或「无」>
- 对比: <HEAD、工作区或路径列表>
- 文件数: <实际阅读的文件数>
- 代码规范: <项目内规范路径，或「未提供」>

## 概要

<两到四句话：审查了什么、最重要的缺陷或风险、是否建议合并或上线。>

| 级别 | 缺陷 | 隐患 | 漏洞 | 规范 | 可优化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| critical | 0 | 0 | 0 | 0 | 0 |
| high | 0 | 0 | 0 | 0 | 0 |
| medium | 0 | 0 | 0 | 0 | 0 |
| low | 0 | 0 | 0 | 0 | 0 |

## 缺陷

未发现问题。

## 隐患

未发现问题。

## 漏洞

未发现问题。

## 规范

未审查。项目未提供 code-review-standards.md、.cursor/code-review-standards.md 或 .cursor/rules。

## 可优化项

未发现问题。

## 未验证项

- <没有运行的测试、没有核对的配置、没有读到的目录>

## 结论

<先处理哪几条，哪些效率问题和规范建议可以以后做。>
````

有发现时，把对应小节里的「未发现问题。」换成发现列表。本次明确不做某一类审查时，该小节只写一行 `未审查。`，并在同一小节说明原因。`standards` 为空时，「规范」必须使用 `未审查。`。有规范文件或 Cursor 规则时，元数据「代码规范」写这些路径。

每条发现使用这个字段顺序：

````markdown
### [BUG-001] 简短标题

- 严重级别: high
- 类别: 空指针
- 位置: `src/order.js:40`
- 置信度: 高
- 问题: <代码现在做了什么>
- 证据: <引用导致问题的具体写法>
- 影响: <对用户、数据或资源的后果>
- 修改建议:
  改前:

  ```text
  <现有代码片段>
  ```

  改后:

  ```text
  <修复后的代码片段>
  ```
- 规范条款: <仅 STD 填写：规范文件路径和被违反的原句>
````

缺陷、隐患、漏洞和可优化项不要写「规范条款」。

规则：

- 编号前缀按小节使用 `BUG`、`RISK`、`SEC`、`STD`、`OPT`，各自从 `001` 连续递增且不重复。
- `严重级别` 只能是 `critical`、`high`、`medium`、`low`。
- `置信度` 只能是 `高`、`中`、`低`。
- `位置` 必须是带反引号的 `路径:行号`。
- 「修改建议」必须同时包含「改前」和「改后」。改后只写修复后的代码。
- `STD` 必须填写「规范条款」，写明规范文件和被违反的原句。
- 概要表的数字必须和正文条数一致。可优化项不要使用 `critical`。
- 某一节没有发现时，正文只能是 `未发现问题。`。
